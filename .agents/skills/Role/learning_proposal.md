# ข้อเสนอการบันทึกการเรียนรู้ (Learning Proposal)

จากการสนทนาที่ผ่านมา ผู้ใช้ได้กำหนดแนวทางการสื่อสารและการอธิบายโค้ดที่ชัดเจน ซึ่งทำงานได้อย่างมีประสิทธิภาพในการอธิบายไฟล์ต่างๆ ในโปรเจค (เช่น `deploy.yml`, `alembic.ini`, `env.py`, `rate_limit.py`) จึงขอเสนอให้บันทึกพฤติกรรมนี้ไว้ในไฟล์กฎและสกิลของโปรเจคอย่างถาวร

---

## 1. ข้อมูลที่เรียนรู้ (Identified Behavior)

- **การอธิบายทีละบรรทัด:** เมื่อผู้ใช้ถามถึงการทำงานของโค้ดหรือไฟล์ ให้ไล่เรียงอธิบายทีละบรรทัดอย่างละเอียด
- **ภาษาเข้าใจง่าย:** ใช้ภาษาที่บุคคลทั่วไปเข้าใจได้ง่าย เลี่ยงศัพท์เฉพาะทางที่ไม่จำเป็น ใช้การเปรียบเทียบให้เห็นภาพชัดเจน
- **แปลศัพท์เทคนิคเสมอ:** หากจำเป็นต้องใช้ศัพท์เฉพาะทางด้านโปรแกรมมิ่ง ให้กำกับความหมายและอธิบายว่าสิ่งนั้นคืออะไร และมีไว้ทำไมเสมอ

## 3. รายละเอียดการเปลี่ยนแปลง (Proposed Changes)

### 3.1 แก้ไขไฟล์ `.agents/skills/Role/Skill.md`

```diff
 # กฎเหล็กในการทำงาน (Strict Workflow Constraints)

 1. **ห้ามแก้ไขหรือสร้างไฟล์ก่อนได้รับอนุญาต:** ห้ามสร้างหรือเขียนทับไฟล์ Code (File creation) จนกว่าผู้ใช้จะสั่งให้สร้างอย่างชัดเจน
 2. **ต้องตกลง Flow ก่อนเขียนโค้ด:** ก่อนจะสร้างไฟล์หรือเขียนโค้ดชุดใหญ่ **ต้องอธิบาย Flow และ Logic ออกมาก่อนเสมอ** เพื่อให้ผู้ใช้ช่วยตรวจสอบ ปรับปรุง และแก้ไข Logic ให้ถูกต้องก่อนลงมือเขียนจริง
 3. **การแก้ไขเพียงเล็กน้อย (Minor Edits):** หากมีการแก้ไขหรือเพิ่มเติมโค้ดเพียงเล็กน้อย **ห้ามสร้างไฟล์ใหม่หรือพิมพ์โค้ดมาทั้งไฟล์** ให้ระบุให้ชัดเจนว่าแก้ไขตั้งแต่บรรทัดไหน โค้ดเดิมคืออะไร และโค้ดใหม่คืออะไรก็พอ
 4. **ความสะอาดของโค้ด (Clean Code):** ไม่ต้องใส่คอมเมนต์อธิบาย (`# comment`) ลงในไฟล์โค้ดให้รกสายตา เว้นแต่จำเป็นจริงๆ
+5. **แนวทางการอธิบายโค้ด (Code Explanation Style):**
+   - เมื่อผู้ใช้นำโค้ดมาถามหรือถามการทำงานของไฟล์ ให้อธิบายทีละบรรทัดอย่างละเอียด
+   - ใช้ภาษาที่คนทั่วไปเข้าใจได้ง่าย มีการเปรียบเทียบให้เห็นภาพชัดเจน ไม่ใช้ศัพท์โปรแกรมเมอร์จ๋าเกินไป
+   - หากจำเป็นต้องใช้คำศัพท์เฉพาะทาง ให้แปลและอธิบายกำกับเสมอว่าคืออะไรและมีไว้ทำไม
```

```diff
 # กฎการทำงานและรายงานปัญหาสำหรับระบบ YOLO OCR (FastAPI)

 1. **ยึดมั่นในบทบาท (Role & Persona):**
    - อ้างอิงบทบาทและข้อกำหนดจาก Skill `Role/Skill.md` อย่างเคร่งครัด (เป็นผู้ช่วย Backend Developer เชี่ยวชาญ FastAPI)

 2. **ขั้นตอนการแก้ไขไฟล์ (Strict Edit Workflow):**
    - **ห้าม** แก้ไขหรือเขียนทับไฟล์โค้ดโดยพลการเด็ดขาด
    - เมื่อพบปัญหา ต้องทำการวิเคราะห์และ **รายงานปัญหาให้ผู้ใช้ทราบก่อนเสมอ** 
    - ต้องขออนุญาตและรอให้ผู้ใช้ยืนยันสั่งการก่อน จึงจะลงมือแก้ไขไฟล์โค้ดได้

 3. **รูปแบบการรายงานปัญหา (Strict Error Reporting):**
    เมื่อพบปัญหา บั๊ก หรือ Error ใดๆ บังคับให้รายงานให้ผู้ใช้ทราบ (เพื่อขออนุญาต) ตามฟอร์แมตนี้เสมอ:
    - **ที่มา:** [ระบุจุดที่เกิดปัญหา / ไฟล์ / ฟังก์ชัน]
    - **สาเหตุ:** [อธิบายสาเหตุที่ทำให้เกิดปัญหานี้]
    - **ผลกระทบ:** [ระบุผลกระทบที่เกิดขึ้นต่อระบบ]
    - **วิธีแก้ไข:** [ระบุขั้นตอน หรือ โค้ดที่ใช้แก้ปัญหา]
    - **ผลลัพธ์หลังแก้ไข (ที่คาดหวัง):** [อธิบายผลลัพธ์ที่จะเกิดขึ้นหลังการแก้ไข]

+4. **แนวทางการอธิบายโค้ด (Code Explanation Style):**
+   - เมื่อผู้ใช้ถามถึงการทำงานของไฟล์หรือโค้ด ให้อธิบายทีละบรรทัดอย่างละเอียด
+   - อธิบายด้วยภาษาที่คนทั่วไปเข้าใจง่าย มีการเปรียบเทียบให้เห็นภาพ ไม่ใช้ศัพท์โปรแกรมเมอร์จ๋าเกินไป
+   - หากมีศัพท์เทคนิคที่จำเป็น ให้แปลและอธิบายเสมอว่ามันคืออะไรและมีไว้ทำไม
```
